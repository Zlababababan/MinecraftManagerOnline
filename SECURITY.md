# Security policy

**English** · [Français](SECURITY.fr.md)

MinecraftManagerOnline exposes a web panel that is meant to be reachable from the Internet, ships
its own Web Push and ACME implementations, and drives Java processes on remote machines. That
surface deserves a policy — even for a project maintained by one person.

## Supported versions

Only the **latest release** receives security fixes. There is no long-term support branch: if you
run an older version, the fix is to update (the one-command installer does it in place, with a
rollback if the new version does not start — see the
[installation guide](docs/guide/installation.md#15-update-the-panel)).

## Reporting a vulnerability

Please report privately, not in a public issue.

1. Go to the repository's **Security** tab and use **Report a vulnerability** (GitHub Private
   Vulnerability Reporting). It keeps the discussion private until a fix is out, and it does not
   require you to know who I am, or me to publish an address.
2. If that button is not available to you, open a normal issue containing **only** the sentence
   "I have a security report" — no details, no reproduction — and I will open a private channel.

Please include, if you can: the version of the panel and of the agents, the installation mode
(one-command installer, archive, Docker), the access mode (Tailscale, direct, manual reverse proxy),
what an attacker needs to start with (nothing? a `viewer` account? a paired machine?), and a
reproduction. The output of `mmo-panel doctor` is often useful.

**What you can expect.** I am a single maintainer working on this in my spare time, so no
service-level promise here would be true. Concretely: I will acknowledge a report as soon as I read
it, and I will tell you honestly whether I intend to fix it, when, and in which release. If a report
is valid and you want credit, you get it in the release notes.

Please do not run automated scanners against a panel that is not yours, and do not test on other
people's servers. A local install takes one command.

## Scope

**In scope** — anything that lets someone do more than they should:

- reaching `/api/*` or `/ws/*` without a session, or bypassing the role required by a route;
- escalating between roles (`viewer` → `operator` → `admin`);
- escaping the per-server file jail of the agent, or writing outside the folders a server owns;
- abusing the pairing flow to attach a machine, or to take over an existing one;
- forging or replaying anything on the panel↔agent WebSocket, or defeating the Ed25519 signature
  that protects the agent auto-update chain;
- secrets leaking where they should not appear — API responses, logs, install commands, backups;
- remote code execution from an unauthenticated position.

**Out of scope** — these are known, documented, and deliberate. Reporting them is not a finding:

- **An administrator can do everything.** Starting processes, reading and writing server files,
  installing a JRE, running console commands: that is the product, not a flaw. Same for an
  `operator` within the servers they are allowed to touch.
- **A panel controls its agents by design.** An agent trusts the panel it paired with — that is the
  control channel. "If I compromise the panel I control the agents" describes the architecture.
- Documented residual debt, listed in `docs/03-socle-technique.md` §6 and accepted for 1.0, all of
  which requires an authenticated account: no SSRF filter on `fs.fetch` (an operator may point it at
  a local or tailnet address), unbounded regex in `logs.search` (ReDoS), newline injection in the
  commands generated by a live `config.set`, no usage counter on the migration relay, and no rate
  limit on the public agent archives.
- **Manual access mode** with a self-signed certificate or a private CA: that is the operator's
  choice, and the guide says what it costs.
- Anything requiring local or physical access to the machine that runs the panel — if someone is
  already on that machine as the panel's user, they have the database.
- Vulnerabilities in Minecraft itself, in mods or plugins you install, or in the Java runtimes the
  agent downloads from Adoptium and Azul. Report those to their authors.
- Missing security headers on the static front-end assets, absent rate limiting on endpoints that
  hold nothing, and reports produced by a scanner without a working reproduction.

## What the project does for you

So you know what is already in place, and what it is not: sessions are random 256-bit tokens stored
hashed, passwords use argon2id, every route denies by default and declares a minimum role, login is
rate-limited by address and by account with a constant-time failure path, the panel listens on
`127.0.0.1` only (`0.0.0.0` is refused at startup unless explicitly opted in for containers), and
the agent refuses to treat its own state or install directory as a server folder.

The Ed25519 signature on release bundles protects the **agent auto-update chain** — it is not a
signature on the archive a human downloads. To check a download, use the `panel-<platform>.json`
manifest published with each release: it carries the expected SHA-256.
