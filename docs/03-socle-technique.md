> **Implémentation (phase 4, `apps/panel`)** : Fastify 5 + `fastify-type-provider-zod` (schémas Zod = validation + types des routes, erreurs de validation → `E_VALIDATION`), `@fastify/websocket` (`/ws/agent`, `/ws/client`), `@fastify/cookie`, Drizzle sur **`node:sqlite`** (adaptateur `src/db/sqlite.ts`, voir l'amendement ci-dessous), `@node-rs/argon2` (argon2id, OWASP m = 19 MiB / t = 2 / p = 1). Le **contrat panel ↔ front** (DTO REST, messages de `/ws/client`, codes d'erreur HTTP) vit dans **`@mmo/protocol/client`**, distinct du protocole panel↔agent mais sous les mêmes règles (jamais `.strict()`). Toute erreur HTTP sort en `{ code, message, retryable, details }`, traduite par l'UI. Config par env : `MMO_DATA_DIR` (défaut `./data`), `MMO_HOST` (défaut `127.0.0.1`, `0.0.0.0`/`::` **refusés au démarrage**), `MMO_PORT`, `MMO_COOKIE_SECURE`, `MMO_MOJANG_MANIFEST`, `MMO_LOG_LEVEL`.

> **Amendement (2026-08-30) — sortie de `better-sqlite3`, driver `node:sqlite`.** Motif : un module natif est un `.node` lié à la glibc de la machine qui l'a construit. C'est ce qui a rendu le panel ininstallable sur une VM Oracle Ubuntu 20.04 ARM64 (aucun prebuild pour Node 24/arm64 → node-gyp → `build-essential`), puis ce qui a cassé les archives Linux des versions 1.0.2 et 1.0.3. `node:sqlite` est embarqué dans le runtime : **plus aucun module natif SQLite, donc plus de plancher de glibc issu du code**.
>
> - **Adaptateur** `apps/panel/src/db/sqlite.ts` : présente la surface de better-sqlite3 réellement consommée (`prepare/exec/pragma/transaction/close`, `run/all/get/raw`). Trois manques de `node:sqlite` y sont comblés — il n'a **ni `pragma()` ni `transaction()`**, ses erreurs n'ont **pas de code `SQLITE_*`** (seulement un `errcode` numérique, traduit ici : sans quoi les gardes `error.code === 'SQLITE_CONSTRAINT_UNIQUE'` de `servers.ts` — course d'adoption — et `=== 'SQLITE_CANTOPEN'` de `main.ts` — message « chown » — deviennent des `if` toujours faux, **sans la moindre erreur visible**), et ses lignes ont un **prototype nul**. Les transactions imbriquées basculent en `SAVEPOINT` comme le faisait better-sqlite3.
> - **Drizzle 0.45.2 n'a pas de driver `node:sqlite`**, et `drizzle-orm/better-sqlite3` importe le module natif dès sa première ligne. La base est donc assemblée dans `db/client.ts` à partir de `BetterSQLiteSession` + `BaseSQLiteDatabase` (sous-chemins `/session` et `/migrator`, vérifiés sans aucun `.node` dans `process.moduleLoadList`) — c'est la recopie du `construct()` du driver. `@types/better-sqlite3` reste en devDependency : le `.d.ts` de la session en dépend (types seulement).
> - **`drizzle-orm/sqlite-proxy` a été écarté** en connaissance de cause : il existe et il est officiel, mais il est **asynchrone** — l'adopter transformerait les 32 services et les tests synchrones du panel en `Promise`.
> - Garde-fou : règle ESLint `no-restricted-imports` (`kind: 'panel'`) sur `better-sqlite3`, `drizzle-orm/better-sqlite3` et `**/*.node`. `GET /api/health` expose `sqlite: { driver, version }`.
>
> **Amendement (2026-08-30) — `mmo-panel setup`, configuration sans navigateur.** Le wizard n'existait qu'en HTTP alors que le panel n'écoute que sur 127.0.0.1 : sur une VM cloud il fallait monter un tunnel SSH ou un `tailscale serve` **avant** de pouvoir créer le premier compte (troisième accroc de l'installation Ubuntu 20.04 ARM). `completeSetup` sort de la closure de route vers `services/setup.ts` — impératif, c'est lui qui génère les clés VAPID, et une seconde implémentation créerait une installation dont le push est mort sans que rien ne le dise. La CLI (`src/cli-setup.ts`) ouvre le contexte complet **sans serveur HTTP** : `--username` plus **une seule** source de mot de passe parmi `--password-stdin` / `--password-file` / `--random-password` (jamais en argument : la ligne de commande est visible de toute la machine), `--locale`, `--public-url` (normalisée par `coerceOrigin` comme dans le wizard), `--access-mode` ; refus si un compte existe déjà.
>
> **Amendement (2026-08-30) — point d'entrée et `mmo-panel doctor`.** `main.ts` n'importe plus rien de l'application au niveau module : il vérifie la version de Node puis charge `boot.ts` (démarrage) ou `doctor.ts` par `await import()`. Motif : un runtime inadapté fait échouer la **construction du graphe de modules**, donc avant la première ligne exécutable et avant l'ouverture du journal — l'utilisateur n'avait qu'une stack de chargeur. `mmo-panel doctor` rend des contrôles `{ code, level, message }` : runtime (version, plateforme, glibc), `node:sqlite` et `@node-rs/argon2` chargés par `createRequire` (argon2 est réellement exercé par un hachage), dossier de données (écriture **réelle** par `openSync('w')` — un `stat` ment sous ACL — et propriétaire comparé à `process.getuid()` avec la commande `chown` exacte), `mmo.db` (`quick_check`), port, front. Sortie 1 dès qu'un contrôle est en erreur. Volontairement borné : ni détection de pare-feu, ni dérive d'horloge, ni reconnaissance de l'hébergeur.

### Pourquoi TypeScript partout (et pas un agent Go)

- La logique « intelligente » de l'agent (détection heuristique, parsing de logs, mapping MC→Java, watchdog) doit exister aussi côté panel : en TS elle vit une fois dans `packages/shared`, en Go elle serait dupliquée ou générée.
- Le gain RAM de Go (~30 Mo vs ~50–140 Mo) est sans valeur sur des machines dimensionnées pour des heaps Java de 4–16 Go (Raspberry Pi 4/5 inclus).
- Le modèle de distribution (§3) neutralise l'avantage single-binary de Go : l'artefact de mise à jour est un unique bundle JS identique pour toutes les plateformes.
- **Condition de bascule assumée** : si la cible devient des machines à 512 Mo–1 Go, réécrire l'agent en Go redevient pertinent. Le protocole versionné (Zod → JSON Schema exportable) borne ce coût : seule l'implémentation de l'agent changerait.

### Bibliothèques sensibles de l'agent

- Process : `child_process.spawn` **détaché** (`detached: true` — indispensable sous Windows, sinon libuv place l'enfant dans un Job Object tué avec l'agent) + stdin/stdout/stderr pipés + persistance PID (voir doc 05, ré-adoption). **Validé par le spike n°1** ([`docs/spikes/01-eof-stdin.md`](spikes/01-eof-stdin.md)) : tous les loaders testés survivent à la mort de l'agent et à l'EOF stdin, restent pilotables par RCON et s'arrêtent proprement.
- Métriques — **amendé le 2026-08-21 par le spike n°2** ([`docs/spikes/02-monitoring-windows.md`](spikes/02-monitoring-windows.md)) : sous Windows, toute comptabilité CPU « par ticks » (`GetProcessTimes`, WMI, compteurs `% Processor Time`, donc `pidusage` et `systeminformation`) est fausse d'un facteur 25–60× dès qu'Hyper-V est actif (WSL2, Docker, VBS). L'agent utilise donc :
  - **Windows** : un **sidecar PowerShell persistant** (script embarqué dans le bundle, P/Invoke `QueryProcessCycleTime` via `Add-Type`, compteur `% Processor Utility` pour la machine) — aucun module natif ; repli `pidusage` + drapeau `cpuSource: 'ticks'` si PowerShell est indisponible.
  - **Linux / macOS** : `pidusage` (`/proc`, `ps`) — comptabilité exacte.
  - `systeminformation` pour l'inventaire (OS, CPU, RAM, volumes) et `mem()`/`fsSize()` périodiques (session `powerShellStart()` sur Windows) ; jamais pour la charge CPU Windows.
  - Les deux bibliothèques fonctionnent **sans `wmic`** (Windows 24H2+), vérifié.

> **Implémentation (phase 7, `apps/agent/src/monitoring/sampler.ts`) — dérogation actée** : **ni `pidusage` ni `systeminformation` ne sont embarqués** (zéro dépendance supplémentaire dans le bundle). Le sidecar PowerShell (script embarqué en chaîne, lancé via `-EncodedCommand`, stdin/stdout JSON ligne à ligne) mesure les **cycles** par processus (`QueryProcessCycleTime`) + RSS (`WorkingSet64`) + `% Processor Utility` ; si `Add-Type` échoue le script bascule lui-même sur `TotalProcessorTime` et le signale (`mode: ticks`) ; si PowerShell ne démarre pas, repli `os.cpus()` machine seule (`cpuSource: 'ticks'`, aucun CPU par processus). Linux : `/proc/<pid>/stat` (utime+stime, CLK_TCK 100) + `/proc/<pid>/status` (VmRSS) + `/proc/stat` (`cpuSource: 'proc'`). macOS : `ps -o pid=,rss=,time=` (temps CPU cumulé → delta) + `os.cpus()` (`'proc'`). RAM machine = `os.totalmem/freemem`, disque = `fs.statfs` du volume de l'état de l'agent. CPU % « en cœurs » (100 = un cœur nominal saturé, borné à `cores × 100`). **Amendé le 2026-09-01** : le repli ticks est **temporaire** (backoff 5/15/30/60 s puis nouvel essai du primaire, journal `process sampler recovered`) — auparavant le premier échec du sidecar, même passager (poignée de main lente sur une machine chargée), privait l'agent du RSS et du CPU par processus jusqu'à son redémarrage ; seule une erreur définitive (PowerShell introuvable) coupe le primaire pour de bon. La poignée de main du sidecar n'utilise plus **aucune requête CIM** (fréquence lue dans le registre, cœurs dans `NUMBER_OF_PROCESSORS`) : une requête WMI peut rester pendante des dizaines de secondes. Le test « burner » du spike n°2 est un test d'intégration de l'agent (`sampler.test.ts`, Windows seulement : > 80 % d'un cœur par cycles, hors CI où la saturation n'est pas garantie) ; un second test, lui, exerce le **démarrage du sidecar et le RSS jusque sur les runners CI**.

- Journal — **ajouté le 2026-09-02 (lot 9)** : chaque ligne du `Logger` (stderr, format texte) est aussi écrite dans `<stateDir>/logs/agent-<date>.log` par `createRotatingLog` de `@mmo/shared/node` (partagé avec le journal du panel : fichier choisi à l'écriture, bascule quotidienne, 32 Mio puis suffixe numéroté, 14 jours ; `fileLog: false` en test). Motif : stderr n'était capturé que par le gestionnaire de service, jamais au même endroit selon l'OS, et le panel ne recevait que WARN/ERROR — sur un incident chez un tiers il n'y avait rien à lire. Le panel en demande la fin par `agent.diagnostics` (doc 05 §3), bornée en lignes et en octets, et la sert masquée.
- RCON : implémentation maison (~100 lignes, protocole trivial) avec file de commandes sérialisée.
- Backups : ~~`archiver` (zip/tar streaming) dans un **worker_thread**~~ — **amendé en phase 8** : tar maison (`packages/shared/src/node/tar.ts` — dans l'agent jusqu'au lot 4, sorti vers `@mmo/shared/node` le 2026-09-02 pour que le panel archive sa base et son `tls/` avec la même mécanique ; ustar + pax, générateur asynchrone + `pipeline()`) dans le processus de l'agent, sans dépendance ni worker (la lecture disque domine ; zstd est natif dans `node:zlib`). Compression par défaut — **amendé le 2026-08-21 par le spike n°3** ([`docs/spikes/03-zstd-node24.md`](spikes/03-zstd-node24.md)) : **zstd niveau 3** (`node:zlib`, Node ≥ 22.15, 5–9× plus rapide que gzip à ratio égal), `checksumFlag` activé, **gzip en repli** (runtime sans zstd ou choix utilisateur). Règles absolues : jamais `ZSTD_c_nbWorkers` (perte silencieuse de données constatée) ; l'intégrité d'une archive repose sur le **manifeste (sha256 + taille)**, jamais sur le codec (un flux zstd tronqué est accepté sans erreur par Node).

## 3. Distribution, installation, mises à jour

### Modèle de distribution (panel et agent, même mécanique)

Archive par plateforme (win-x64, linux-x64, linux-arm64, darwin-arm64) = `runtime/` (Node officiel épinglé) + `app/` (bundle JS) + `launcher.js` + outil de service. Les archives agent sont **embarquées dans la release du panel et servies par lui** :

- Windows : `irm https://<panel>/install.ps1 | iex`
- Linux/macOS : `curl -fsSL https://<panel>/install.sh | sh`

### Installation du panel en une commande (2026-09-01, lot 2)

`apps/panel/install/install-panel.sh` (POSIX sh, Linux/systemd, servi en asset de release GitHub — le panel n'a pas de panel amont) : télécharge `panel-<plat>.json` puis l'archive depuis `releases/latest/download/` (ou `--version`, ou `--archive` hors ligne), vérifie sha256, refuse musl. **Séparation code/données/config** : code `/opt/mmo-panel` (remplacé à chaque mise à jour, bascule `.new`→`.old`), données `/var/lib/mmo-panel` (jamais touchées, `StateDirectory`), réglages `/etc/mmo-panel/panel.env` (jamais écrasé ; `MMO_DATA_DIR` n'y vit PAS — cycle interdit, et l'unit borne les écritures via `ReadWritePaths`). Unit générée depuis le **gabarit versionné embarqué dans l'archive** (`app/install/mmo-panel.service.tmpl` — une seule source, réécrite à chaque update, personnalisation par drop-in `systemctl edit`) : durcissement complet **sauf** `MemoryDenyWriteExecute` (tue V8), `AmbientCapabilities=CAP_NET_BIND_SERVICE` (port 443 du mode direct), `ExecStartPre=-… doctor`, `ExecStart` via `mmo-panel.sh` (pas de chemin de runtime codé en dur dans l'unit). Relancer le script = **mise à jour** : sauvegarde de `mmo.db` d'abord, swap, `systemctl restart` explicite (`enable --now` ne redémarre pas un service actif), attente de `/api/health` **avec comparaison de version**, rollback vers `.old` sinon (version en échec conservée en `.failed`). Rétrocompat : des données dans `<dir>/data` sont détectées, préservées à travers les swaps et jamais déplacées ; `--migrate-data` opt-in (copie, `integrity_check` via node:sqlite embarqué, suppression de l'ancien dossier seulement après redémarrage sain). Jamais de lecture stdin (`curl | sh` : stdin est le script). Exercé en CI sur `debian:11` nu (pose hors ligne, doctor, mise à jour par-dessus des données à l'ancien emplacement).

**Docker** : image multi-stage `node:24-bookworm-slim` (la réponse à Alpine/musl — l'image emporte sa libc ; aucun runtime épinglé), étape finale non-root (`USER node`), healthcheck sans curl (fetch du runtime), `VOLUME /data` possédé par `node` (compose recommande le volume nommé — un bind `./data` créé par root = SQLITE_CANTOPEN reproduit). `MMO_ALLOW_ANY_INTERFACE=1` : opt-in **explicite et bruyant** (warn au boot) qui lève le refus de `0.0.0.0` — jamais déduit d'une détection de conteneur (échoue en Podman rootless) ; posé par l'image, la ligne `ports:` du compose décide de l'exposition réelle. Image officielle publiée par `release.yml` sur ghcr.io (buildx amd64+arm64, arm64 sous QEMU) avec les archives d'agents de la release déposées dans `docker/dist-agent/` (entrypoint : `MMO_DIST_DIR=/app/dist-agent` si présent et non surchargé — sans agents, défaut `<dataDir>/dist` sur le volume, le dépôt admin y persiste). CI : l'image est construite ET démarrée sur chaque PR (`/api/health`, warn vérifié, `doctor`).

**Bannière « version X disponible »** : `services/update-check.ts` lit `releases.atom` (pas d'API GitHub, pas de quota) au plus 1 fois/6 h — timer dédié de 30 min dans `buildApp` (PAS `runMaintenance` : les tests l'appellent directement, et un appel au démarrage ferait sortir chaque panel de test sur GitHub ; aucun panel de test ne vit 30 min), auto-limitation par `panel.update.checkedAt` horodaté AVANT l'appel (GitHub en panne n'est pas martelé). Le flux Atom liste tout (pré-releases comprises, titres libres, ordre chronologique) : on parse les tags `/releases/tag/vX.Y.Z` stricts (pré-releases exclues) et on prend le max par `compareVersions`. Événement `panel.updateAvailable` publié une fois par version (`panel.update.notifiedVersion`), catégorie de notification `panel.update` (groupe `panel`, cloche oui / push non par défaut). Exposition front par `/api/auth/me` (`panelUpdate`, admins seulement), bannière dans le Shell (fermeture par version en localStorage). Réglage `panel.updateCheck.enabled` (défaut activé) : un panel auto-hébergé ne doit pas être forcé de parler à GitHub.

**Windows** : `install-panel.ps1` (même contrat — asset de release, sha256, `.new`/`.old`, health+version+rollback, `-Uninstall [-Purge]`) : code `%ProgramFiles%\mmo-panel`, données `%ProgramData%\mmo-panel`, service **shawl** recréé à chaque passage (le chemin `runtime\<v>\node.exe` est re-résolu — un bump de `.node-version` ne casse plus le service), démarrage `delayed-auto`, `LocalSystem` par défaut (`-ServiceAccount User` + SeServiceLogonRight via secedit pour les lecteurs réseau), choix (`-Port`, compte…) mémorisés dans `%ProgramData%\mmo-panel\install.json` et relus à la mise à jour, `-MigrateFrom` copie les données d'une installation manuelle (integrity_check, original jamais modifié — la suppression reste à l'utilisateur). Auto-élévation UAC calquée sur `install.ps1` de l'agent. **Icône de zone de notification** : `mmo-panel-tray.ps1` (WinForms NotifyIcon, zéro dépendance), raccourci menu Démarrer posé par l'installeur ; l'icône PILOTE le service quand il existe (Start/Stop/Restart élevés à la demande, jamais un second panel) et sinon lance le panel en enfant (« Quitter » l'arrête — arrêt abrupt assumé, WAL) ; « Démarrer avec Windows » = raccourci shell:Startup par utilisateur. Pièges PowerShell notés dans les scripts : BOM UTF-8 obligatoire (5.1 lit le sans-BOM en ANSI, un « — » devient une smart quote qui FERME les chaînes), `-LiteralPath` (crochets = glob), pas de guillemets imbriqués dans un `node -e` (passage d'arguments natif < 7.3).

### Démarrage au boot

- **Windows** : service via **shawl** (embarqué dans l'archive ; fallback documenté : WinSW). **Identité : compte de l'utilisateur** (pas LocalSystem — ACL sur les dossiers serveurs, lecteurs mappés). À tester sur un poste réel.
- **Linux** : unit systemd (`User=mmo`, `Restart=on-failure`).
- **macOS** : LaunchDaemon (`KeepAlive=true`).
- **Contrainte commune (spike n°1)** : le superviseur ne doit **jamais tuer l'arbre de processus** de l'agent, sinon les serveurs Java tombent avec lui. Un `taskkill /T` sur l'agent tue les serveurs détachés (constaté) ; idem `KillMode=control-group` (défaut systemd) ou un groupe de processus launchd. À imposer en phase 11 : systemd `KillMode=process` (ou serveurs lancés dans un scope transient), launchd `AbandonProcessGroup=true`, Windows : vérifier que shawl/WinSW n'enrôlent pas l'enfant dans un Job Object « kill on close » — test dédié par OS.

### Mise à jour de l'agent (modèle unifié — fait autorité)

1. Chaque release du panel embarque le bundle agent de même version + sha256 + **signature Ed25519**. La clé privée de signature vit **chez le mainteneur** (jamais sur le panel) ; la clé publique est embarquée dans l'agent — un panel compromis ne peut pas pousser du code arbitraire.
2. Au `auth.hello`, l'agent annonce sa version ; le panel propose `agent.update` (politique auto ou validation admin).
3. L'agent télécharge **depuis le panel** le bundle universel, vérifie sha256 + signature, écrit `versions/x.y.z/`, note `next.json`, sort avec le code **75**.
4. Le **launcher** (~150 lignes, figé, sur-testé, jamais mis à jour par ce canal) bascule `current` (junction/rename — pas de symlink sous Windows), relance. **Health-check : WS + heartbeat rétablis sous 30 s et pas 2 crashs**, sinon rollback automatique vers N-1 + signalement.
5. **Les serveurs Minecraft ne tombent jamais** : processus Java détachés, ré-adoptés au redémarrage de l'agent (vérification PID **+ heure de démarrage du process + ligne de commande** — jamais le PID seul). Stdin perdu jusqu'au prochain restart du serveur → pilotage RCON entre-temps (mode `detached`).
6. Le **runtime Node** a son propre canal (`runtime.update`, rare) : téléchargement de l'archive runtime, swap par le launcher au prochain restart.

## 5. Couche d'accès (pluggable — aucune API Tailscale dans le code)

Contexte réseau de référence : machine hôte en **IPv6 seul, IPv4 CGNAT, pas de redirection de ports** — mais les deux cas (traversée VPN et exposition directe) sont gérés.

| Mode                     | Mécanique                                                           | HTTPS                                                                                                     | Pour qui                                                                 |
| ------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **`tailscale`** (défaut) | Tailnet privé ; panel derrière `tailscale serve` (écoute 127.0.0.1) | Cert Let's Encrypt auto pour `panel.<tailnet>.ts.net`                                                     | 100 % des amis (traverse CGNAT/4G/hôtel) ; plan gratuit = 6 utilisateurs |
| **`direct`**             | Domaine perso + AAAA vers la box, pinholes pare-feu IPv6            | **ACME DNS-01 intégré au panel** + client DynDNS intégré (mise à jour de l'AAAA au changement de préfixe) | Amis avec IPv6 de bout en bout ; aucune app à installer                  |
| **`manual`**             | Reverse-proxy/certificats fournis par l'utilisateur                 | À sa charge                                                                                               | Configurations avancées                                                  |

Faits vérifiés qui imposent ce design :

- PWA, service worker et Web Push exigent un **contexte sécurisé HTTPS** (seule exception : localhost) — même dans un tailnet.
- Le **push sort sur Internet** (FCM/Apple/Mozilla) : le panel a besoin d'Internet sortant pour notifier, quel que soit le mode.
- **iOS ≥ 16.4** : push uniquement pour la PWA **installée sur l'écran d'accueil** → onboarding guidé + re-synchronisation périodique des abonnements (iOS purge silencieusement).

**Jeu (connexion Minecraft des amis)** : réglage **par serveur** — `tailnet` ou `direct` — le panel affiche l'adresse exacte à donner aux amis pour chaque mode + test de joignabilité intégré. Minecraft Java gère l'IPv6 nativement.

Portabilité : si Tailscale change ses conditions → **Headscale** (serveur de contrôle open-source auto-hébergé, mêmes clients) ou mode `direct`, sans toucher au code MMO.

> **Lot 2 (2026-09-01) — une voie d'accès PAR MACHINE.** Le mode n'est plus exclusif : `access.direct.enabled` (`false` par défaut, Réglages → Accès) arme la voie directe **en plus** du mode courant — `AccessService.directEnabled()` (= mode `direct` OU réglage) remplace les gates `mode === 'direct'` de `start()`, `doIssue()`, `firewallRules()` et du bloc `direct` du statut ; le PATCH des réglages `access.*` **réapplique la couche à chaud** (`restart()` : timers + listener HTTPS, sans redémarrer le panel). ## 6. Sécurité (résumé)

- Panel : écoute uniquement sur 127.0.0.1 (mode tailscale) ou sur l'interface dédiée — jamais `0.0.0.0`. _Phase 10_ : le listener HTTPS du mode `direct` se lie à l'adresse publique explicite (`access.publicHost`) ou à l'IPv6 globale détectée, jamais à `::` ; `/ws/probe` est public mais ne fait qu'un écho borné (15 s, taille de frame limitée par `maxPayload`) ; le jeton DNS (`access.dns.token`) est un secret d'`app_settings` jamais renvoyé par l'API (seul `access.dns.token.set` l'est).
- Sessions cookie (token haché en base), argon2id, RBAC admin/opérateur/lecture. _Phase 4_ : cookie `mmo_session` (256 bits aléatoires, SHA-256 en base, `HttpOnly`, `SameSite=Lax`, `Secure` si `panel.publicUrl` est en https ou `MMO_COOKIE_SECURE=1`, 30 jours) ; **refus par défaut** — toute route non marquée `public` exige une session, rôle minimal par route (`viewer` < `operator` < `admin`) ; login limité à 10 essais/min par IP+compte ; le dernier admin actif ne peut être ni rétrogradé ni supprimé ; désactivation/changement de rôle/mot de passe = sessions révoquées. `/ws/client` authentifie par le même cookie à l'upgrade. _Phase 5_ : la surface protégée est **`/api/*` et `/ws/*`** ; tout le reste (fichiers du front, fallback SPA) est public — le front ne contient aucun secret, les données passent toujours par l'API.
- _Lot 8 (2026-09-03)_ : **droits par serveur et par machine**. `users.scoped = 1` limite un compte (jamais un admin) aux portées de `user_server_permissions` / `user_machine_permissions` (rôle `viewer` | `operator` par ligne, plafonné par `users.role` — cap réappliqué à la lecture) ; `services/permissions.ts` calcule le rôle effectif (serveur accordé > machine accordée qui couvre ses serveurs ; un serveur accordé rend sa machine `viewer`). **Trois points de branchement** : le hook d'auth juge le rôle effectif sur toute route `/api/servers/:id…` ou `/api/machines/:id…` (`request.params` est rempli par le routeur dès `onRequest`) et répond **404** hors portée (aucune énumération) ; le hub refuse l'abonnement à un canal console hors portée (`E_NOT_FOUND`) et filtre chaque message diffusé par `serverId`/`machineId` (l'échantillon de métriques d'une machine partagée est retaillé aux serveurs accordés) ; les listes (`/api/servers`, `/api/machines`, `/api/tasks`, `/api/schedules`, `/api/events`, conflits, centre de notifications et push) filtrent. `bulk-action` juge serveur par serveur ; une action de groupe exige `operator` sur chacun de ses membres. Changer `scoped` révoque les sessions comme un changement de rôle ; changer les portées ferme les WebSockets du compte (code `4002`, le front se reconnecte et relit `me`). Hors portée (macros, actions groupées), `users.role` vaut tel quel.
- _Lot 8 (2026-09-03)_ : **clés d'API** (`services/api-keys.ts`, table `api_keys`) — le modèle des sessions copié : 256 bits aléatoires en base64url derrière le préfixe `mmo_`, seul le SHA-256 en base (index unique), résolution par égalité du hachage puis `safeEqualHex`, `lastUsedAt`/`lastUsedIp` touchés au plus une fois par minute. Le hook d'auth tente `Authorization: Bearer` **seulement sans cookie** (le cookie prime), jamais sur `/ws` ni sur une route `public`, avec un limiteur par adresse sur les jetons refusés (30/min → 429) ; jeton mal formé, inconnu, expiré ou propriétaire inactif → 401 `E_AUTH` `reason INVALID_API_KEY`. Le rôle porté par la requête est le **plus faible** entre la clé et son propriétaire au moment de la requête (`weakerRole`), et `PermissionsService.snapshotFor(user)` redescend les portées accordées d'un compte limité à ce même rôle — une clé n'élève jamais un compte. À la création, rôle ≤ celui du propriétaire (`E_VALIDATION KEY_ABOVE_ROLE`), défaut `viewer`, 32 clés par compte (`TOO_MANY_KEYS`) ; une rétrogradation redescend les clés en base (`clampToRole`), une désactivation les rend muettes, une suppression les emporte (cascade). **Routes réservées au cookie** (`sessionOnly` : `/api/auth/*` sauf `GET /api/auth/me`, `/api/users*`, `/api/api-keys*`, `/api/setup*`) → 403 `E_FORBIDDEN reason API_KEY` : une clé volée ne devient jamais un accès durable. Journal d'accès : champ `apiKey` (préfixe) ; audit : `username` = `compte [mmo_xxxxxxxx…]` pour toute action faite par une clé, jamais le jeton (le préfixe seul est audité à la création). Maintenance : clés expirées purgées 30 j après leur expiration (listées « expirée » d'ici là).
- _Lot 8 (2026-09-03)_ : **voir et révoquer ses sessions** — `GET /api/auth/sessions` (sessions vivantes du compte, `current` = celle de la requête, `request.sessionId` posé par le hook d'auth), `DELETE /api/auth/sessions/:id` (la sienne seulement, sinon 404 ; la courante = déconnexion, cookie effacé), `DELETE /api/auth/sessions` (toutes sauf la courante), `DELETE /api/users/:id/sessions` (admin). Le hub connaît la session qui a ouvert chaque socket (`attach(ws, user, sessionId)`, `disconnectSession`) : révoquer UNE session ferme SES sockets en `4001` et laisse les autres appareils ouverts. Routes réservées au cookie (une clé d'API → 403).
- _Lot 8 (2026-09-03)_ : **page de statut publique** (`services/status-pages.ts`, table `server_status_pages`) — une deuxième surface anonyme du panel, après `/api/health` et la distribution. Elle est **fermée par défaut** (aucune ligne tant que personne n'en demande une), activée serveur par serveur, et n'expose qu'un DTO construit à la main (`publicStatusSchema`) : nom, état simplifié, adresse à copier, version, MOTD, joueurs, prochaine sauvegarde — jamais un chemin, une machine, un PID ni un identifiant. Le jeton (128 bits, base64url) est le seul secret : stocké **en clair** parce qu'il faut le réafficher pour le partager, il n'ouvre qu'une lecture et se remplace d'un clic (l'ancien meurt aussitôt) ; le limiteur public (`PublicRateLimits`, surface `status`, 120/min par adresse, en `preValidation` pour compter aussi les jetons mal formés) couvre l'énumération. Jeton inconnu, page désactivée, serveur archivé ou supprimé rendent le **même 404**. Les pseudos des joueurs ne sortent qu'avec l'opt-in `show_players` (doc 04 §8.6), décoché par défaut. Rien du passage d'un visiteur n'est conservé : la télémétrie d'interface s'arrête au préfixe `/s/`, la page ne charge aucune ressource tierce (pas d'avatar `mc-heads.net`), et le journal d'accès ne garde que le motif de route. Le résultat est mis en cache (15 s, promesse partagée entre requêtes concurrentes) et le repli **Server List Ping** n'est tenté que si aucun agent ne tient la machine — dix amis qui rafraîchissent ne font ni dix requêtes à l'agent, ni dix pings.
- _Lot 8 (2026-09-04)_ : **boutons dans la notification** (`pushActionsFor` dans `services/notifications.ts`, `pushActionSchema` côté protocole, `apps/web/public/sw-push.js`). Règle : **le panel décide, le worker exécute**. Le raisonnement — quelle action pour quel événement, quelle URL, quels textes — vit dans une fonction pure du panel, donc testée ; le service worker ne fait qu'appeler ce qu'on lui donne. Il garde tout de même sa propre garde, parce que c'est le seul endroit du produit qui peut MODIFIER quelque chose depuis un écran verrouillé : une action ne peut viser qu'un chemin interne (`/api/…` pour un appel, un chemin du panel pour une navigation), une URL absolue ou protocole-relative est refusée, et l'appel part avec `credentials: 'same-origin'` — donc soumis aux mêmes droits que l'interface. Le résultat revient en notification (la notification d'origine disparaît au clic ; sans retour on taperait dans le vide), avec des textes fournis par le panel. **Le worker est désormais sous test** (`apps/web/src/lib/sw-push.test.ts`) : le fichier est évalué avec un faux `self`, et ce sont bien ses écouteurs livrés qui décident d'appeler ou de refuser.
- _Lot 8 (2026-09-04)_ : **heures calmes et silence par serveur** (`users.quiet_from/quiet_to`, table `notification_mutes`, migration `0020` — deux ADD COLUMN et un CREATE, pure). Un seul point de branchement : `pushAllowed(userId, event)` dans `deliver`, jamais dans `list` — la cloche garde tout, c'est la leçon de la phase 10 (couper une catégorie la retirait des deux canaux). `inQuietHours` est **pure** et gère la traversée de minuit (`from > to`, le cas normal), borne basse incluse et haute exclue ; une plage vide (`from === to`) ne fait rien taire. `isCriticalForQuietHours` laisse passer `severity === 'error'` **et** `alert.firing` — cette famille porte `warning` alors qu'elle nomme précisément les urgences du produit. L'heure murale vient du fuseau **du panel** (`settings.timeZone()`), pas du processus. La mise en silence passe par `PUT /api/servers/:id/notifications` : sous `/api/servers/:id`, donc la portée par serveur du lot 8 s'y applique déjà et un identifiant inventé répond « introuvable ».
- _Lot 8 (2026-09-04)_ : **statistiques de fréquentation** (`services/player-stats.ts`, `GET /api/servers/:id/players/stats?days=`) — lecture pure de `player_sessions`, sans agent ni écriture. Deux requêtes SQL portées par les index existants (`(server_id, joined_at)`) : les sessions qui **touchent** la fenêtre (ouvertes comprises — d'où le `left_at IS NULL OR left_at > from`, un `joined_at >=` seul perdrait la partie en cours) et un `min(joined_at)` groupé pour « nouveaux joueurs ». Le calcul vit dans une fonction **pure** : une grille d'heures murales est construite une fois pour la fenêtre (`Intl` coûte cher : une fenêtre d'un an sur un serveur fréquenté ferait des centaines de milliers d'appels si chaque session recalculait ses bornes), puis chaque session la parcourt. Trois propriétés que les tests attaquent : une session qui déborde de la fenêtre ne compte que sa part et une session ouverte s'arrête à `now` ; une session à cheval sur minuit se partage entre les deux journées ; les journées de 23 h et de 25 h sont comptées telles quelles (l'heure murale 2 h peut avoir lieu deux fois). Le fuseau est celui du panel (`schedule.timezone`), jamais celui du processus — même leçon que les planifications, doc 05 §3. Fenêtre bornée à 366 jours, top borné à 10, rien de publié hors du panel (ni page de statut, ni notification, ni webhook) et la portée par serveur du lot 8 s'applique comme sur toute route nommant un serveur.
- _Lot 8 (2026-09-04)_ : **demande de whitelist en libre-service** (`services/whitelist-requests.ts`, table `whitelist_requests`) — la seule **écriture** anonyme du produit. Elle ne crée pas de surface : elle réutilise le jeton de la page de statut (`POST /api/status/:token/whitelist`) et n'est ouverte que par un second opt-in par serveur (`allow_whitelist`), un jeton valide dont la page ne l'a pas ouvert rendant le même 404 qu'un jeton inventé. La règle qui la rend sûre : **une demande est inerte** — le panel valide (`MINECRAFT_NAME_RE`, 3–16 caractères `[A-Za-z0-9_]`, mot ≤ 200), range une ligne et publie un événement ; il n'appelle ni l'agent, ni Mojang, n'écrit aucun fichier de serveur et ne met rien en mouvement. Une entrée anonyme ne doit jamais déclencher un travail sur le parc de quelqu'un ; c'est aussi pourquoi le **mot du visiteur ne part pas dans l'événement** (il finirait en notification push et en webhook Discord sans qu'un humain l'ait relu) alors que le pseudo, contraint par le motif, peut être cité. Limiteur dédié (`PublicRateLimits`, surface `whitelist`, **10/min par adresse** via `PUBLIC_SURFACE_MAX`, toujours borné par le plafond général) : une écriture n'a pas le même budget qu'une lecture. Unicité (serveur, pseudo en minuscules) : insister ne crée pas de doublon et rend l'état de sa propre demande — le seul canal par lequel un ami accepté apprend qu'il peut se connecter. Tout le reste est authentifié : la liste (lecture), Accepter (opérateur, `player.action whitelistAdd` — l'action existante, l'agent choisissant commande ou fichier et résolvant le pseudo selon `privacy.mojangLookup`), Refuser, Oublier ; la décision n'est écrite **qu'après** le succès de l'action, sinon la demande reste en attente plutôt que de promettre une place que personne n'a. Rien du visiteur n'est conservé (ni adresse, ni horodatage de visite) et la table est bornée par un plafond de maintenance qui épargne les demandes en attente.
- Secrets d'agent : 256 bits, hachés côté panel, rotation/révocation. Codes d'appairage : hachés, TTL 15 min, 5 essais, rate-limit.
- L'authentification applicative des agents est **obligatoire même sous Tailscale** (les appareils des amis sont dans le tailnet ; Tailscale authentifie des machines, pas des rôles).
- **Port RCON** : bloqué hors machine locale (règle pare-feu posée par l'agent + ACL réseau documentée) — il écoute en clair sur toutes les interfaces.
- Bundles agent signés Ed25519 (§3).

(8) `migration.finalize` ne renomme/purge que le dossier enregistré pour ce `serverId` ; (9) les manifestes de sauvegarde ne désignent plus un `archivePath` arbitraire (archive toujours à côté du manifeste → `backup.delete` ne supprime plus un fichier quelconque) ; (10) chemins **réservés** : corbeille (`.mmo-trash`, casse ignorée) et marqueur `.mmo-server.json` à la racine refusés comme cible de `write`/`mkdir`/`rename`/`copy`/upload/`fs.fetch` et comme source de `delete`/`rename` (un `rename` vers `.mmo-trash/0-x` valait suppression définitive à la purge) ; noms de périphériques Windows et segments à point/espace final refusés.

Cookie `SameSite=Lax` + JSON sans parser `form/multipart` = pas de CSRF exploitable ; pas de vérification d'`Origin` sur `/ws/client` (défense en profondeur possible).
> **Dette traitée (phase 12, 2026-08-23)** : `/ws/probe` borné (8 sondes simultanées → 1013, frame > 256 Kio ou > 4 Mio cumulés → 1009, 15 s) ; `/api/setup` : limiteur 5/min par adresse en `preValidation` (un corps invalide compte) + verrou en vol (`E_BUSY`), deux POST concurrents ne créent qu'un admin ; bornes de taille : `fs.fetch` 8 Gio (taille annoncée, `content-length`, puis flux réel ; `.part` supprimé) et **schéma http(s) seulement**, upload 64 Gio et jamais au-delà de la taille déclarée (`TransferReceiver` laisse passer la `ProtocolError` du consommateur), extractions tar/zip 64 Gio et 2 M d'entrées avec, pour le zip, un compteur sur le flux **inflaté** (en-tête menteur) — nouveau code `E_TOO_LARGE` (HTTP 413, non réessayable). Tests : `panel/http/hardening.test.ts`, `agent.backup.test.ts` (phase 12), `shared/node/tar.test.ts` (déplacé avec le module, lot 4), `java/zip.test.ts`.
> **Dette traitée (2026-08-30)** : toute clé de limiteur dérivée d'une adresse passe par `clientKey()` (`util/rate-limit.ts`) — IPv4 telle quelle, IPv6 **ramenée à son /64**, forme `::ffff:` traitée comme de l'IPv4 : un abonné IPv6 disposait sinon de 2^64 clés, donc d'aucune limite, et la carte du limiteur grossissait d'une entrée par tentative jusqu'à la purge en O(n). Le login gagne un **second limiteur par adresse seule** (30/min) en plus de `adresse|compte` (10/min), sans quoi faire varier le nom d'utilisateur suffisait à ne jamais être limité. Timing d'énumération : `users.authenticate` vérifie désormais le mot de passe contre un **hachage factice** (`dummyPasswordHash()`, calculé une fois) quand le compte est inconnu ou désactivé — les trois chemins d'échec coûtent le même temps.

> **Dette traitée (2026-09-02, lot 9) — surfaces publiques limitées et contre-pression WebSocket.** `http/rate-limits.ts` (`PublicRateLimits`, `ctx.rateLimits`) : une fenêtre glissante **par adresse** (`clientKey`) et **par surface** — `relay` (`/api/relay/:token`, en `preHandler` : un jeton inconnu compte aussi), `distribution` (`/dist/*`, `install.sh|ps1`, `/api/dist*`) et `ws-agent` (poignée de main `/ws/agent`, fermée `1013` au-delà — l'appairage était limité, pas la connexion, donc pas les tentatives d'`auth.hello`) — **120 requêtes/min** par défaut (un agent qui reprend un bundle par tranches `Range` en fait quelques dizaines), refus `429 E_RATE_LIMITED` retryable. **Contre-pression** (`@mmo/protocol` `rpc/backpressure.ts`, `backpressureAction`) : l'envoi n'inspectait jamais `bufferedAmount` alors que les deux transports l'exposent. Politique en deux paliers, identique des deux côtés : au-delà de **1 Mio** en attente, les messages **de faible valeur** — `metrics.sample`, `console.lines`, remplacés par les suivants — sont abandonnés (compteur, un `warn` par épisode, `panel reading again` à la reprise côté agent) ; au-delà de **8 Mio**, le panel ferme le socket du navigateur (`1013 client too slow`, le front se reconnecte). Les états, événements et réponses passent toujours. Côté agent (`connection.ts` `trySend`), les événements critiques ne sont jamais abandonnés : ils sont journalisés et rejoués. Tests : `clients/hub.test.ts`, `http/rate-limits.test.ts`, `rpc/backpressure.test.ts`, `connection.test.ts`.
> **Dette traitée (2026-09-02, lot 4) — webhooks sortants et garde SSRF.** Un webhook est une URL choisie par un administrateur vers laquelle le panel fait un POST depuis SA machine : sans filtre, c'est un relais vers tout ce que cette machine voit (le panel lui-même sur 127.0.0.1, les agents, un NAS, les métadonnées d'un cloud sur 169.254.169.254, le tailnet en 100.64/10 et fd7a:…). `services/webhooks/ssrf.ts` pose trois barrières dans l'ordre — l'URL (schéma `https:` seul, identifiants refusés, forme `discord.com/api/webhooks/<id>/<jeton>` exigée pour le genre Discord), le nom d'hôte (noms sans point, `.local`, `.lan`, `.internal`, `.home.arpa`, `.ts.net`… refusés AVANT résolution), puis CHAQUE adresse résolue (v4 : 0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.168/16, 192.0.0/24, 198.18/15, plages de documentation, 224/4, 240/4 ; v6 : `::`, `::1`, `fe80::/10`, `fc00::/7`, `ff00::/8`, `2001:db8::/32`, et les IPv4 embarquées des formes mappée, compatible, NAT64 et 6to4 ramenées au contrôle v4). L'adresse retenue est **épinglée** : le transport (`webhooks/transport.ts`, `node:https` avec l'option `lookup` de `net.connect`) se connecte à elle en gardant le nom pour le SNI et `Host`, ce qui ferme le rebinding DNS entre validation et envoi ; aucune redirection n'est suivie (un 3xx revient comme échec définitif), la réponse est lue au plus 64 Kio, délai 15 s. La garde s'applique à la saisie (400 `E_VALIDATION`, `details.reason` = `BAD_URL` | `BAD_SCHEME` | `CREDENTIALS` | `BLOCKED_HOST` | `BLOCKED_ADDRESS` | `UNRESOLVABLE` | `NOT_DISCORD`, traduits par l'UI) ET à chaque envoi. Le secret HMAC d'un webhook JSON (256 bits hex) est montré une fois à la création et à la rotation, jamais renvoyé par l'API ni consigné dans l'audit (URL masquée aussi : jeton Discord remplacé, query string retirée). Tests : `webhooks/ssrf.test.ts` (plages, noms, URL, résolution mixte), `webhooks/transport.test.ts` (vrai serveur local : adresse épinglée vs nom fictif, 302 non suivi, réponse bornée, délai), `webhooks/signature.test.ts`, `http/webhooks.test.ts`. La dette « pas de filtre SSRF sur `fs.fetch` » (agent, ci-dessous) reste ouverte : ce filtre-ci vit côté panel.
> **Dette restante (actée pour 1.0)** : pas de filtre SSRF sur `fs.fetch` (URL locale/tailnet) ; `logs.search` avec regex non bornée (ReDoS) ; injection de `\n` dans les commandes générées par `config.set` live ; `/api/relay` migration sans compteur d'usage.

- **Règle protocole** : `error.message` = anglais technique (logs) ; l'UI traduit à partir de `error.code` + `error.details`. Idem pour les textes de push (localisés par le panel selon la langue du destinataire).

> **Amendement (2026-09-02, lot 9) — journal d'accès corrélé et `/api/health` diagnostique.** La journalisation des requêtes de Fastify reste désactivée (deux lignes anonymes par requête) au profit d'un hook `onResponse` maison (`apps/panel/src/http/access-log.ts`) : **une ligne `request` par réponse** sur la surface `/api`, `/ws`, `/dist`, `install.sh|ps1` — jamais le front — avec `requestId` (**ULID** via `genReqId`, unique entre redémarrages ; c'est la valeur qu'un 500 renvoie dans `details.requestId`), méthode, **motif de route** (`/api/servers/:id`, jamais l'URL ni la query string, qui peuvent porter un chemin ou un pseudo), statut, durée, utilisateur, adresse. `warn` dès 500 ou au-delà d'**une seconde** (`SLOW_REQUEST_MS`, surchargeable en test), `debug` pour la sonde de santé anonyme (Docker et les installeurs l'appellent toutes les 30 s). Transitions muettes journalisées en `info` : action planifiée exécutée (`scheduled action executed`), agent connecté/déconnecté (déjà), lignes purgées (doc 04 §8.6). **`GET /api/health`** reste public et inchangé pour les sondes ; une session **administrateur** y reçoit en plus `diagnostics` : `startedAt`, `uptimeSec`, `logFile` (fichier courant, relu à chaque appel — il bascule chaque jour), `machines { total, connected }`, `databases { mmo, metrics }` (chemin + octets WAL compris), `maintenance` (dernier passage : instant, durée, tables purgées non nulles, issue du VACUUM par fichier). Test : `http/access-log.test.ts`.

## 8. Premier démarrage (bootstrap)

Wizard first-run : si la table `users` est vide → création du compte admin (endpoint verrouillé ensuite), génération des clés VAPID, choix du répertoire data et de la destination de backups par défaut, choix du mode d'accès. Rien de tout cela n'est fait « à la main ».

> **Implémentation (phase 4, API)** : `GET /api/setup/status` → `{ needsSetup }` ; `POST /api/setup { username, password, locale?, publicUrl?, accessMode?, backupDestination? }` crée l'admin, génère les clés VAPID (P-256 via `node:crypto`, privée jamais exposée par l'API), enregistre les réglages et ouvre la session ; `E_SETUP_DONE` ensuite. Tant qu'aucun utilisateur n'existe, les routes protégées répondent `E_AUTH` avec `details.setupRequired = true` (le front redirige vers le wizard). **Dérogation** : le répertoire data se choisit **par l'environnement** (`MMO_DATA_DIR`), pas dans le wizard — la base doit exister avant la première page.

> **Budgets de performance (2026-09-02, lot 9)** — le régime réel est 53 serveurs, un échantillon toutes les 15 s par serveur, une diffusion à chaque navigateur ; rien dans le plan n'en faisait une assertion. Le test d'échelle (`integration/scale.test.ts`, 56 serveurs réels détectés + 48 h de métriques synthétiques) élève trois mesures au rang de **bornes qui font échouer** (valeurs mesurées le 2026-09-02 imprimées en `[budget]`, bornes à ~1,5–2,7×) : (1) **taille de `GET /api/servers`** pour 56 serveurs — mesuré **105 227 o** (≈ 1,9 Kio par serveur), borne `SERVERS_LIST_MAX_BYTES` 160 Kio — un DTO qui embarquerait la détection ou un journal ferait sauter la borne ; (2) **instructions SQL par rendu de la liste** — mesuré **3**, borne `SERVERS_LIST_MAX_STATEMENTS` 8 — grâce au compteur `SqliteHandle.stats.statements` de l'adaptateur `node:sqlite` (`run/get/all/exec`) : un N+1 ne peut plus s'installer sans bruit ; (3) **ce qu'un navigateur inactif reçoit** pendant le rejeu de 48 h de métriques — mesuré **4 messages sur 11 520 échantillons ingérés**, borne `IDLE_CLIENT_MAX_SAMPLE_MESSAGES` 20 — et le poids d'un `metrics.sample` de 56 serveurs — mesuré **6 499 o**, borne `SAMPLE_MESSAGE_MAX_BYTES` 12 Kio (soit ~26 Kio/min par machine à 15 s). La troisième borne a un correctif derrière elle : `context.ts` ne diffuse aux navigateurs que les échantillons **vivants** (`ts` < 60 s, `LIVE_SAMPLE_WINDOW_MS`) — un agent qui se reconnectait rejouait jusqu'à une heure de tampon, soit 240 messages par navigateur pour des points qu'aucune vue n'affiche en direct. Métrique **`agent.self`** : `agentRssMb` / `agentCpuPct` dans chaque heartbeat (`monitoring/self.ts`, delta de `process.cpuUsage()`), affichés sur la carte Agent — « il ralentit mon serveur » devient vérifiable.

> **CI réelle (post-1.0, 2026-08-25)** : première exécution à la publication du dépôt (aucun remote avant) — la matrice 4 OS + le job `release-archives` tournent et sont verts. Stabilisation en deux lots : (1) fragilités ponctuelles des tests (fixtures de logs commitées après exception au `.gitignore`, archives factices multi-OS, tolérances d'hôte via `it.runIf`) ; (2) remèdes **systémiques** de cadence, en un point : helpers `waitFor` ×3 sur CI + `testBudget()` pour les budgets d'`it`, `testTimeout` vitest 180 s (agent/panel) / 60 s (web) sur CI, `retry: 2` sur CI seulement — le local reste strict et rapide. Le retry a débusqué un vrai bug de harnais (plage RCON `[rconFrom, 65000]` vide quand le port éphémère dépasse 65000 → clamp 64 000). Deux tests restent tolérants-CI (`[flaky-ci]` : warn au lieu d'échec, stricts en local) : phase9 releases/rollback (Linux/ARM) et métriques RSS/TPS Windows — instabilités documentées, débogage à prévoir. Côté produit, la CI a fait émerger le disjoncteur CIM de `process-info` (doc 06 §1).

> **Implémentation (phase 5, e2e)** : `pnpm --filter @mmo/web e2e` — Playwright construit le front puis lance `e2e/fixtures/stack.ts` (`webServer`) : **panel réel** (sources `apps/panel/src`, SQLite temporaire, port `MMO_E2E_PORT` = 3999) servant le build, **agent réel** (sources `apps/agent/src`) dont Java est remplacé par le fake Java server, un serveur Vanilla minimal ; routes de pilotage `/e2e/*` (hors production). ## 10. Spikes de validation (réalisés le 2026-08-21 — voir [docs/spikes/](spikes/README.md))

1. **Comportement EOF stdin** — ✅ [confirmé](spikes/01-eof-stdin.md) : Vanilla 1.20.1, Forge 1.12.2/1.16.5, Fabric 1.21.1, NeoForge 1.21.1 survivent tous à la mort de l'agent et à l'EOF, restent pilotables par RCON et s'arrêtent proprement. Le modèle « serveurs détachés, stdin principal + RCON » est retenu tel quel ; la variante « java sans stdin, 100 % RCON » n'est pas nécessaire. Conditions : `detached: true` (Windows) et superviseur qui ne tue jamais l'arbre de processus (§3).
2. **Monitoring Windows 11 24H2+** — ✅/❗ [résultat](spikes/02-monitoring-windows.md) : `systeminformation` et `pidusage` n'utilisent plus `wmic` ; mais la comptabilité CPU par ticks est fausse sous Hyper-V → sidecar PowerShell + `QueryProcessCycleTime` (§1). Le fallback « CIM maison » initialement prévu aurait été faux lui aussi.
3. **zstd dans Node 24** — ✅ [validé](spikes/03-zstd-node24.md) : API streaming complète (Node ≥ 22.15), 5–9× plus rapide que gzip → zstd 3 par défaut, gzip en repli ; interdits/garde-fous en §1.
